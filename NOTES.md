## 1. Что сделано

- Задача 1: Распределение заказов
    - П. 1: Исправлена ошибка в findNearest: координаты филиала передавались в неверном порядке.
    - П. 2-4: Реализовано распределение заказов по филиалам, правила pickup_point и city, географическая проверка, дневные лимиты, API назначения заказа и получения загрузки филиала. Добавлена идемпотентность.
    - П. 5: При запуске нескольких экземпляров сервиса с общей БД данные о назначениях должны храниться централизованно. Текущий in-memory массив для этого не подходит. Также необходимо учитывать параллельные запросы, чтобы избежать повторного назначения заказов и превышения лимитов филиалов.

- Задача 2: Бронирование
    - П. 1: Исправлена ошибка в overlaps: соседние интервалы (10:00–11:00 и 11:00–12:00) ошибочно считались пересекающимися. Оператор <= заменён на <.
    - П. 2: Реализовано получение свободных слотов с учётом расписания, перерывов и существующих бронирований.
    - П. 3: Реализовано создание бронирования с проверкой телефона, доступности слота и защитой от конкурентных запросов через Mutex.
    - П. 4: Реализована отмена бронирования с двухчасовым ограничением и поддержкой повторной отмены.
    - П. 5: В production я бы использовал PostgreSQL: транзакцию с SELECT FOR UPDATE для блокировки операций одного мастера и EXCLUDE USING GIST для запрета пересекающихся активных бронирований на уровне БД.


- Структура проекта: код разделён на контроллеры, сервисы, утилиты и общие типы для удобства сопровождения.

## 2. Принятые допущения

- manual не проверяет дневной лимит, но занимает место в филиале.
- Названия городов сравниваются без учёта регистра и лишних пробелов.
- unassigned сохраняется, поэтому повторный запрос возвращает тот же результат.
- Время начала бронирования должно точно совпадать со свободным слотом, иначе возвращается 409.
- Принимаются только казахстанские мобильные номера с поддерживаемыми префиксами.
- Отмена ровно за два часа до начала разрешена. Запрет действует только при остатке времени менее двух часов.
